# Практическая работа №1

**Тема:** Основные положения теории баз данных, хранилищ данных, баз знаний

## 1. Цель и порядок выполнения работы

**Цель:** изучить различия в назначении, архитектуре, структурах хранения и механизмах защиты информации между транзакционными базами данных (OLTP), аналитическими хранилищами данных (DWH/OLAP) и базами знаний (KB) на примере конкретной предметной области.

**Порядок выполнения:**

1. Ознакомиться с предметной областью согласно номеру своего варианта (раздел 2).
2. Спроектировать транзакционный уровень (OLTP): составить спецификацию ключевых таблиц (3НФ), определить первичные (PK) и внешние (FK) ключи, типы данных и ограничения целостности.
3. Спроектировать аналитический уровень (DWH): составить схему «звезда» (Star Schema), включающую таблицу фактов (с числовыми метриками) и 3–4 таблицы измерений.
4. Разработать базу знаний (KB): составить не менее 3 продукционных правил логического вывода в формате «ЕСЛИ ... ТО ...».
5. Заполнить сводную таблицу сравнения архитектурных уровней и указать методы защиты данных для каждого уровня.
6. Ответить на контрольные вопросы.

## 3. Эталонный образец выполнения (Вариант №1: «Городская поликлиника»)

### 3.1. Транзакционный уровень (OLTP)

**Назначение:** автоматизация работы регистратуры и кабинетов врачей, фиксация выданных талонов и расписания в режиме реального времени.

#### Спецификация реляционных таблиц (3НФ)

1. Таблица `Patients` (Пациенты):
   - `patient_id` (INT, PRIMARY KEY, AUTO_INCREMENT) — уникальный номер карты пациента;
   - `oms_policy` (VARCHAR(16), UNIQUE, NOT NULL) — 16-значный номер полиса ОМС;
   - `full_name` (VARCHAR(100), NOT NULL) — ФИО пациента;
   - `birth_date` (DATE, NOT NULL) — дата рождения;
   - `phone_number` (VARCHAR(15), NOT NULL) — номер контактного телефона.

2. Таблица `Specialities` (Справочник специальностей):
   - `speciality_id` (INT, PRIMARY KEY) — код специальности;
   - `speciality_name` (VARCHAR(50), NOT NULL) — наименование специальности (терапевт, хирург, офтальмолог и т.д.).

3. Таблица `Doctors` (Врачи):
   - `doctor_id` (INT, PRIMARY KEY, AUTO_INCREMENT) — табельный номер врача;
   - `full_name` (VARCHAR(100), NOT NULL) — ФИО врача;
   - `speciality_id` (INT, FOREIGN KEY -> Specialities.speciality_id) — код специализации;
   - `cabinet_num` (VARCHAR(5), NOT NULL) — номер закрепленного кабинета.

4. Таблица `Appointments` (Талоны на прием):
   - `appointment_id` (BIGINT, PRIMARY KEY, AUTO_INCREMENT) — уникальный номер записи;
   - `patient_id` (INT, FOREIGN KEY -> Patients.patient_id) — пациент;
   - `doctor_id` (INT, FOREIGN KEY -> Doctors.doctor_id) — принимающий врач;
   - `appointment_datetime` (DATETIME, NOT NULL) — дата и время приема;
   - `status` (VARCHAR(20), NOT NULL) — статус талона (`забронирован`, `завершен`, `отменен`);
   - Ограничение целостности: `UNIQUE(doctor_id, appointment_datetime)` — запрет двойной записи к одному врачу на одно время.

**Методы защиты данных OLTP-уровня:**

- Разграничение прав доступа (RBAC): регистраторы имеют доступ только к вставке записей и контактным данным; врачи — к медицинским диагнозам;
- Криптографическая защита: шифрование персональных данных (ФИО, полис ОМС, телефон) в соответствии с требованиями 152-ФЗ «О персональных данных»;
- Журналирование (Audit Trail): фиксация в неизменяемом журнале всех операций чтения, изменения и удаления медицинских записей с фиксацией IP-адреса и ID учетной записи.

### 3.2. Аналитический уровень (DWH)

**Назначение:** консолидация исторических срезов за несколько лет для оценки пропускной способности поликлиники, сезонной заболеваемости и выработки персонала.

#### Модель «Звезда» (Star Schema)

**Центральная таблица фактов: `Fact_Visits` (Факты состоявшихся приемов)**

- `fact_id` (BIGINT, PRIMARY KEY) — суррогатный ключ факта;
- `date_key` (INT, FK -> Dim_Date.date_key) — дата приема;
- `doctor_key` (INT, FK -> Dim_Doctor.doctor_key) — врач;
- `patient_demography_key` (INT, FK -> Dim_Patient_Demography.demography_key) — демографическая группа;
- `diagnosis_key` (INT, FK -> Dim_Diagnosis.diagnosis_key) — установленный диагноз;
- _Числовые показатели (метрики):_
  - `waiting_time_minutes` (INT) — время фактического ожидания в коридоре перед приемом;
  - `consultation_duration_minutes` (INT) — длительность приема врачом;
  - `service_cost_rub` (DECIMAL(10,2)) — стоимость приема по тарифной сетке территориального фонда ОМС.

**Таблицы измерений:**

1. `Dim_Date` (Измерение календарного времени):
   - `date_key` (INT, PK) — формат YYYYMMDD;
   - `full_date` (DATE);
   - `day_of_week` (VARCHAR(15));
   - `month` (TINYINT);
   - `quarter` (TINYINT);
   - `year` (SMALLINT);
   - `is_epidemic_season` (BOOLEAN) — признак сезонной эпидемии гриппа/ОРВИ.
2. `Dim_Doctor` (Измерение медицинского персонала):
   - `doctor_key` (INT, PK) — суррогатный ключ;
   - `doctor_natural_id` (INT) — исходный ID из OLTP;
   - `full_name` (VARCHAR(100));
   - `speciality_title` (VARCHAR(50));
   - `experience_years` (TINYINT) — стаж;
   - `qualification_tier` (VARCHAR(30)) — квалификационная категория.
3. `Dim_Diagnosis` (Измерение классификатора МКБ-10):
   - `diagnosis_key` (INT, PK);
   - `icd10_code` (VARCHAR(10)) — код по международной классификации (например, J06.9);
   - `disease_name` (VARCHAR(150)) — наименование нозологии;
   - `disease_class` (VARCHAR(100)) — класс болезни (болезни органов дыхания, кровообращения и др.).
4. `Dim_Patient_Demography` (Обезличенное измерение пациентов):
   - `demography_key` (INT, PK);
   - `age_group` (VARCHAR(20)) — возрастная когорта (`0-17`, `18-35`, `36-60`, `60+`);
   - `gender` (CHAR(1)) — пол (`M`/`F`);
   - `district_number` (INT) — номер прикрепленного медицинского участка.

**Методы защиты данных DWH-уровня:**

- Полная деперсонализация (обезличивание): в DWH не передаются ФИО, телефон, паспортные данные и точные адреса;
- Сегментация прав: доступ к аналитическим кубам предоставляется только администрации и аналитикам через защищенные VPN-туннели.

### 3.3. Интеллектуальный контур (База знаний / Экспертная система)

**Назначение:** первичный триаж (сортировка) пациентов через терминал самозаписи, интеллектуальная маршрутизация обращения и выявление экстренных ситуаций.

#### Продукционные правила базы знаний (модель «ЕСЛИ ... ТО ...»)

- **Правило №1 (Критическое состояние / Экстренный вызов):**
  - **ЕСЛИ:** `Симптом_Одышка == ДА` **И** (`Температура_тела >= 39.0` **ИЛИ** `Цианоз_губ == ДА`)
  - **ТО:** `Категория_срочности = "Экстренная"`, `Назначить_действие = "Блокировка терминала, вызов дежурного реаниматолога / СМП"`, `Звуковое_оповещение = ВКЛ`.

- **Правило №2 (Маршрутизация при кардиологическом риске):**
  - **ЕСЛИ:** `Жалоба == "Давящая загрудинная боль"` **И** `Возраст > 45` **И** `Иррадиация_в_руку_челюсть == ДА`
  - **ТО:** `Категория_срочности = "Неотложная"`, `Направить_к = "Врач-кардиолог"`, `Назначить_предварительно = "Снятие ЭКГ в доврачебном кабинете"`.

- **Правило №3 (Плановая терапевтическая маршрутизация):**
  - **ЕСЛИ:** `Жалоба == "Кашель"` **И** `Температура_тела < 37.8` **И** `Длительность_дней <= 3` **И** `Одышка == НЕТ`
  - **ТО:** `Категория_срочности = "Плановая"`, `Направить_к = "Участковый терапевт"`, `Талон_резерв = "Зеленый коридор (дежурный врач)"`.

**Методы защиты базы знаний:**

- Контроль целостности правил: вычисление криптографических контрольных сумм (SHA-256) файлов базы правил для исключения несанкционированного изменения логики;
- Экспертная верификация: применение электронной цифровой подписи (ЭЦП) главного врача при утверждении и загрузке новых правил в продукционную среду.

### 3.4. Сводный сравнительный анализ уровней

| Параметр сравнения              | Транзакционная база данных (OLTP)                                 | Аналитическое хранилище данных (DWH)                                | База знаний (KB)                                                        |
| ------------------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| **Главная цель**                | Регистрация текущих фактов и оперативное обслуживание пациентов   | Комплексный ретроспективный анализ и построение отчетности          | Логический вывод, экспертная классификация и поддержка принятия решений |
| **Характер запросов**           | Быстрые, точечные запросы (`INSERT`, `UPDATE`, `SELECT` по ключу) | Тяжелые сканирующие выборки с агрегацией (`SUM`, `AVG`, `GROUP BY`) | Логическая дедукция, сопоставление с образцом по продукционным правилам |
| **Нормализация**                | Высокая (3-я нормальная форма, исключение дублирования)           | Низкая (денормализованная схема фактов и измерений)                 | Не применимо (графы знаний, деревья решений, фреймы)                    |
| **Объем и актуальность данных** | Текущие оперативные данные (дни, недели, месяцы)                  | Исторические срезы за несколько лет (накопление без удаления)       | Статичный или периодически обновляемый свод правил и аксиом             |
| **Ключевой вектор защиты**      | Защита от утечки ПДн (152-ФЗ), разграничение прав доступа (RBAC)  | Маскирование и агрегация данных для исключения деанонимизации       | Защита целостности базы правил от вредоносной подмены алгоритмов вывода |
