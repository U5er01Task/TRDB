**Тема:** Структуры данных СУБД, общий подход к организации представлений, таблиц, индексов и кластеров

## 1. Цель и порядок выполнения работы

**Цель:** изучить внутренние структуры хранения данных в реляционных СУБД, научиться проектировать оптимизированные таблицы, создавать обычные и материализованные представления (Views), подбирать типы индексов (B-Tree, Hash, GIN, частичные и составные), а также применять кластерное упорядочение (Clustered Index / `CLUSTER`) для ускорения доступа и защиты данных.

**Порядок выполнения:**

1. Ознакомиться с предметной областью и нагрузкой на базу данных согласно своему варианту (раздел 2).
2. **Проектирование таблиц:** написать DDL-скрипт создания 2–3 взаимосвязанных таблиц с оптимальными типами данных.
3. **Организация представлений (Views):**
   - Создать **обычное представление** (`VIEW`) для скрытия чувствительных столбцов (реализация безопасности и логической независимости);
   - Создать **материализованное представление** (`MATERIALIZED VIEW`) для тяжелой аналитической агрегации и описать стратегию его обновления.
4. **Проектирование индексов:**
   - Создать минимум 3 индекса: составной (Composite), частичный (Partial, с условием `WHERE`) и покрывающий (`INCLUDE`) или полнотекстовый (`GIN`);
   - Обосновать выбор типа индекса под типовые запросы предметной области.
5. **Кластеризация данных:**
   - Определить, по какому индексу целесообразно физически кластеризовать основную таблицу (`CLUSTER table USING index` в PostgreSQL или кластерный индекс в MS SQL/InnoDB), и объяснить эффект для дискового ввода-вывода (I/O).
6. Ответить на контрольные вопросы.

## 3. Эталонный образец выполнения (Вариант №1: «Банковские транзакции»)

### 3.1. Проектирование базовых таблиц (PostgreSQL)

    CREATE SCHEMA IF NOT EXISTS bank_core;
    SET search_path TO bank_core, public;

    -- Таблица филиалов банка
    CREATE TABLE branches (
        branch_id SERIAL PRIMARY KEY,
        branch_code VARCHAR(10) NOT NULL UNIQUE,
        city VARCHAR(50) NOT NULL
    );

    -- Таблица счетов клиентов
    CREATE TABLE accounts (
        account_id BIGSERIAL PRIMARY KEY,
        account_number CHAR(20) NOT NULL UNIQUE,
        card_pan_masked VARCHAR(19) NOT NULL, -- Маскированный номер карты
        card_pan_encrypted BYTEA NOT NULL,    -- Зашифрованный полный номер
        branch_id INT NOT NULL REFERENCES branches(branch_id),
        balance NUMERIC(15, 2) NOT NULL DEFAULT 0.00
    );

    -- Высоконагруженная таблица транзакций
    CREATE TABLE transactions (
        tx_id BIGSERIAL PRIMARY KEY,
        source_account_id BIGINT NOT NULL REFERENCES accounts(account_id),
        target_account_id BIGINT NOT NULL REFERENCES accounts(account_id),
        amount NUMERIC(15, 2) NOT NULL CHECK (amount > 0),
        tx_status VARCHAR(15) NOT NULL CHECK (tx_status IN ('success', 'failed', 'pending')),
        tx_timestamp TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
        details JSONB -- Дополнительные метаданные (IP, терминал, код ошибки)
    );

### 3.2. Организация представлений (Views и Materialized Views)

#### 1. Обычное представление (защита персональных данных)

Создается для операционистов и службы поддержки, чтобы скрыть зашифрованные бинарные данные карт и внутренние идентификаторы.

    CREATE OR REPLACE VIEW v_safe_account_transactions AS
    SELECT
        t.tx_id,
        a_src.account_number AS sender_account,
        a_src.card_pan_masked AS sender_card,
        a_dst.account_number AS receiver_account,
        t.amount,
        t.tx_status,
        t.tx_timestamp
    FROM transactions t
    JOIN accounts a_src ON t.source_account_id = a_src.account_id
    JOIN accounts a_dst ON t.target_account_id = a_dst.account_id;

#### 2. Материализованное представление (тяжелая аналитика)

Предварительно рассчитывает суточный оборот по каждому филиалу, чтобы не перегружать основную таблицу `transactions` тяжелыми агрегациями `SUM` и `GROUP BY`.

    CREATE MATERIALIZED VIEW mv_daily_branch_turnover AS
    SELECT
        b.branch_code,
        b.city,
        DATE(t.tx_timestamp) AS tx_date,
        COUNT(t.tx_id) AS total_tx_count,
        SUM(t.amount) AS total_turnover_rub
    FROM transactions t
    JOIN accounts a ON t.source_account_id = a.account_id
    JOIN branches b ON a.branch_id = b.branch_id
    WHERE t.tx_status = 'success'
    GROUP BY b.branch_code, b.city, DATE(t.tx_timestamp)
    WITH DATA;

    -- Уникальный индекс для возможности обновления без блокировки чтения (CONCURRENTLY)
    CREATE UNIQUE INDEX idx_mv_branch_date
        ON mv_daily_branch_turnover (branch_code, tx_date);

### 3.3. Проектирование индексов под нагрузку

1. **Составной B-Tree индекс** для быстрого поиска истории операций конкретного счета с сортировкой по времени:

   CREATE INDEX idx_tx_source_time
   ON transactions (source_account_id, tx_timestamp DESC);

2. **Частичный (Partial) индекс** только для ошибочных транзакций. Занимает минимум места на диске, так как успешные операции (99% таблицы) в него не попадают:

   CREATE INDEX idx_tx_failed_only
   ON transactions (tx_timestamp)
   WHERE tx_status = 'failed';

3. **GIN-индекс** для быстрого поиска по полуструктурированным метаданным (например, поиск всех транзакций с конкретного IP-адреса или кода терминала внутри `JSONB`):

   CREATE INDEX idx_tx_details_gin
   ON transactions USING GIN (details);

### 3.4. Кластерная организация таблицы

Поскольку большинство аналитических и регламентных выборок запрашивают транзакции за определенный период (например, «за последние сутки» или «за месяц»), физическое расположение строк на диске вразброс вызывает множество случайных чтений (Random I/O).

**Решение:** кластеризация таблицы `transactions` по индексу временной метки.

    -- 1. Создаем B-Tree индекс по времени транзакции
    CREATE INDEX idx_tx_timestamp ON transactions (tx_timestamp);

    -- 2. Физически переупорядочиваем строки таблицы на диске согласно этому индексу
    CLUSTER transactions USING idx_tx_timestamp;

**Эффект:** записи за один и тот же день/час оказываются в соседних страницах памяти (8 КБ). Диапазонные запросы (`WHERE tx_timestamp BETWEEN ...`) начинают работать через последовательное чтение (Sequential I/O), что ускоряет выборку в несколько раз.
