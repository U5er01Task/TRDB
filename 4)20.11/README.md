# Самостоятельная работа №3

**Тема:** Анализ планов выполнения запросов, аудит индексирования и оптимизация структур хранения данных в СУБД  
**Форма контроля:** Электронный отчет с SQL-кодом и выводами

---

## 1. Цель и задачи работы

**Цель:** научиться выявлять узкие места производительности в реляционных базах данных с помощью анализаторов планов запросов (`EXPLAIN ANALYZE`), устранять избыточное или неэффективное сканирование таблиц, проектировать покрывающие индексы и оценивать влияние структур хранения на безопасность.

**Задачи для самостоятельного выполнения:**

1. Изучить предоставленную в варианте проблемную ситуацию (медленный запрос, утечка данных через представление или деградация индекса).
2. Диагностировать причину проблемы (например: полное сканирование `Seq Scan`, отсутствие индекса на внешний ключ, нарушение порядка столбцов в составном индексе, отсутствие ограничения доступа).
3. Написать SQL-скрипт, устраняющий проблему (создание покрывающего индекса `INCLUDE`, функционального индекса, настройка `SECURITY BARRIER` или рефакторинг `VIEW`).
4. Оформить краткое аналитическое обоснование: почему предложенное решение работает быстрее и безопаснее.

## 3. Эталонный разбор задания (Вариант №1)

### Проблема:

В таблице `users` есть индекс `CREATE INDEX idx_users_email ON users(email);`.  
Однако запрос:
SELECT user_id, full_name FROM users WHERE LOWER(email) = 'ivan@mail.ru';
выполняется медленно и в плане `EXPLAIN ANALYZE` показывает `Seq Scan on users` (полное сканирование таблицы).

### Причина:

Обычный B-Tree индекс хранит исходные значения столбца `email` с учетом регистра (например, `'Ivan@Mail.ru'`). Когда к столбцу в условии `WHERE` применяется функция `LOWER(email)`, СУБД не может использовать дерево индекса напрямую, так как в индексе нет предварительно вычисленных значений в нижнем регистре.

### Решение:

1. Удалить неиспользуемый индекс (если регистрозависимый поиск не нужен) и создать **функциональный индекс (Expression Index)**:

   DROP INDEX IF EXISTS idx_users_email;
   CREATE INDEX idx_users_email_lower ON users (LOWER(email));

2. Обновить статистику таблицы, чтобы планировщик сразу учел новый индекс:

   ANALYZE users;

### Результат:

После создания функционального индекса в дереве B-Tree будут храниться сразу преобразованные строки в нижнем регистре. Повторный запуск `EXPLAIN ANALYZE` покажет `Index Scan using idx_users_email_lower`, а время выполнения сократится с десятков миллисекунд до долей миллисекунды.
